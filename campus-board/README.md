# 珠科雷达

面向在校学生、重点照顾新生使用体验的校园活动与机会信息板。26 条模拟信息全部来自本次考核题目第四部分。

> 珠科雷达是学生作品，不是学校官方平台。页面内的活动信息均为考核用的模拟数据。

## 三个页面

| 页面 | 文件 | 职责 |
| --- | --- | --- |
| 主入口页（第一屏） | `index.html` | 校徽 + 产品名 + 一句话主张，选择进入学生端或管理端；首屏锁定，点「学生端」平滑滚到第二屏 |
| 学生端（第二屏） | `index.html` | 信息板本体：搜索、筛选、状态推算、变更时间线、收藏、发布。`radar.html` 是同一套内容的独立入口，留着方便单独打开 |
| 管理端 | `admin.html` | 审核学生提交的信息：待审核 / 已通过 / 已驳回 |

学生发布的信息不会直接公开，流程是：**提交 → 待审核 → 管理端审核 → 通过 → 进入公开信息流**。
审核状态存在浏览器本地（与学生端共用同一份 localStorage），因此不需要账号、权限或后端；
`pending` 表示还没进公开列表，与学生端已有的「待核实」（已公开但内容需要留意）是两件事。

## 解决什么问题

校园里的机会信息是**散的**：训练营的通知发在群里，场地变更补在另一条消息里，讲座不写地点，兼职信息只留一个私人微信。对熟悉情况的老生，这些都不是问题；对新生，则是「不知道该不该去、还来不来得及、这条消息可不可信」。

珠科雷达不是把信息再罗列一遍，而是把每条信息翻译成三个学生真正要判断的问题：

1. **还来不来得及** —— 状态全部由时间基准推算，不是写死的文案；
2. **这条信息变过没有** —— 补充通知合并成一条，展示「改了什么」；
3. **这条信息能不能信** —— 缺什么就标什么，可疑的地方直说。

## 核心功能

**① 自动判断状态。** 全站以题目要求的时间背景 `2026年9月19日（周六）14:00` 为默认时间源，推出「还剩 22 小时截止」「今天 15:00 开始」「报名已截止 · 可候补」「提取信息 9月22日 周二失效」「已结束」等状态。顶栏显示了这一基准，旁边一个 `↻ 使用当前时间` 的小开关可以切到真实时间再看一遍——不设定时器、不做时间旅行，切回基准即可复现评审时的状态。

**② 补充通知合并。** 材料里 01（训练营）与 09（场地变更通知）、03（团队招募）与 20（名额变化说明）本来是同一条信息的两个版本。列表里只出现一条主信息，详情里用时间线显示「起初发布 → 补充通知，以及当前生效的是哪一版」。

**③ 找得到。** 关键词搜索 + 来源（学校/学院、学生发布、主办方未标注）、类型、状态三组筛选，默认按「还能不能赶上」排序，让最紧急的排在最前面。

**④ 收藏与本地保存。** 收藏、我发布的内容都存在浏览器本地，刷新和重新打开都还在，不需要登录。

**⑤ 学生自己发布。** 约球、组队、找搭子都可以发，发布后进入正常信息流，并出现在「我发布的」里。

**⑥ 个人面板。** 收藏、我发布的、发布入口都收在左上角「我的」抽屉里，筛选区只留搜索和三组条件；进入收藏或我发布的视图时，列表上方会出现「正在看 xx / 返回全部信息」的返回条。

**⑦ 首页入口区。** 首屏给出一句主张和三个来自真实数据的入口（今天有安排 / 24 小时内截止 / 学生自发且待核实），点一下就等于应用对应筛选并跳到信息板。右侧校园剪影用 SVG 代码绘制，没有引入外部图片或依赖。

## 自主设计的实用功能：发布前先做一次「信息体检」

题目里最麻烦的一类信息不是假的，而是**缺的**：#06 没写报名时间、#12 没写费用、#16 没写截止时间、#22 场地待定、#24 要求加私人微信。这些信息单看都「没问题」，凑在一起就是新生踩坑的来源。

所以把判断前置到发布环节：学生填表时实时提示「没填活动时间」「没填地点」「没填报名截止」，出现「日结 / 零门槛」「加私人微信」这类表述时明确提示风险。发布之后，这些提示会变成信息卡上的标签，让同学一眼看出哪些内容还需要自己再确认。

平台不会因为缺信息就拒绝发布，也不会替发布者补一个地点或日期——**开放发布和提醒风险同时做到**。

## 主动发现并处理的一个关键问题

材料 01 写「原计划 9月20日起每周六 19:00 训练」，但 9 月 20 日在 2026 年是**周日**，与「每周六」自相矛盾；紧接着 09 号补充通知又把首次训练改成 9月21日 19:30、地点改到实验楼A402。

这带来一个真实的产品判断：三个时间点在打架时，页面应该显示什么。这里的处理是——

- 详情里默认显示**最新生效**的时间（9月21日 19:30，实验楼A402）；
- 同时保留原始信息，并注明「原计划 9月20日 19:00，已按补充通知更新」，让人看得出改动；
- 对无法判断的部分不做推算：#18 只写「每两周一次」，不替它编出下一次的日期；#11 没写地点就写「未提供」。

「以最新通知为准」这件事由界面明确表达，而不是让用户自己对比两条消息。

## 运行方式

**在线地址：<https://maIQ250.github.io/git/>**

打开即用：进入主入口页 → 点「学生端」进入信息板，点「管理端」进入审核台。不需要安装、不需要注册、不需要后端。

本地运行（可选，纯前端零依赖，不需要 `npm install`）：

```bash
# 直接双击打开
campus-board/index.html

# 或者起一个本地静态服务器
npx serve campus-board
```

线上版本由 GitHub Actions 发布到 GitHub Pages，仓库根地址即为本项目。

## 自动化测试

```bash
node --test campus-board/tests/logic.test.mjs
```

10 个用例守着最容易出错的地方：26 条信息是否齐全、补充通知是否正确合并、状态是否由基准时刻算出、材料没写的信息是否仍标为「未提供」、高风险表述是否被识别。

## 项目结构

| 文件 | 职责 |
| --- | --- |
| `index.html` | 主入口页（第一屏）+ 学生端（第二屏）：顶栏、搜索筛选区、信息列表、详情栏、发布弹窗，以及首屏锁定与滚动脚本 |
| `portal.css` | 入口页样式（变量加 `p-` 前缀，避免与学生端样式表互相覆盖） |
| `radar.html` | 学生端的独立入口，内容与第二屏一致 |
| `styles.css` | 学生端基础样式、导航栏、信息卡、状态色与响应式布局 |
| `app.js` | 状态推算、补充通知合并、筛选搜索、收藏、发布体检与审核状态展示 |
| `data.js` | 26 条模拟信息的结构化数据（题目原文，未做推测补全） |
| `admin.html` / `admin.css` / `admin.js` | 管理端审核台：待审核 / 通过 / 驳回 |
| `assets/campus.png`、`assets/school-logo.png` | 校园照片与校徽，从用户提供的设计稿中裁出 |
| `tests/logic.test.mjs` | 数据与判断逻辑的自动化测试 |

## 下一步最想完善的

1. **来源可信度做成可积累的机制**：现在是一次性提示，理想状态是按发布者历史记录形成长期可信度，同时保留新发布者的正常曝光机会。
2. **订阅与提醒**：把「还剩 22 小时截止」变成主动提醒，而不是等人打开页面才看到。
3. **真实的多用户发布**：目前发布内容存在浏览器本地，只能自己看到；接入后端后可以让发布内容真正进入公共信息流，并配合审核与举报处理。
