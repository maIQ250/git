# 校园失物招领系统 —— 设计文档

- 日期：2026-09-14（初版）、2026-09-15（第 2 版）
- 状态：已与需求方确认（第 2 版），待实现
- 开发分支：`codex/lost-found`
- 项目目录：`lost-found/`

> 第 2 版变更：需求方明确系统要做成「失物招领柜」——物品由管理员登记进系统，
> 学生打开页面就能看到柜子里现在放着什么。初版把系统设计成了「学生发帖、管理员审核」的论坛模型，
> 与真实场景不符，本版修正了角色分工、发布规则与状态流转。

## 1. 目标与范围

做一个可以真实运行的校园失物招领系统，包含学生端和管理员端两个入口。
管理员把收到的实物登记进系统（拍照、拾获地点、拾获时间），学生打开页面就能看到
失物招领柜里现在放着什么，认出自己的东西后提交认领申请；管理员处理申请并把物品标记为已归还。
管理员另外负责审核学生发布的寻物启事、管理全部信息、管理用户、查看数据概览。

数据保存在服务端的 SQLite 数据库中，多个学生通过浏览器访问同一个服务时看到的是同一份数据。

### 本期做

- 两个入口：学生端、管理员端
- 基于学号的注册与登录、基于服务端会话的身份保持
- 招领物品登记（管理员，含照片）、浏览、搜索、筛选、详情、编辑、删除
- 寻物启事发布（学生）、审核、浏览
- 单张图片上传与展示
- 认领申请闭环：申请 → 管理员处理 → 同意后自动标记已归还
- 管理员审核寻物启事、物品管理、用户封禁、数据概览
- 服务端输入校验、权限检查与统一错误响应
- 自动化测试（接口测试 + 页面端到端冒烟）

### 本期不做（非目标）

- 不做邮件 / 短信验证，不做找回密码
- 不做实时通知、站内聊天
- 不做图片压缩、多图上传、裁剪
- 不做 HTTPS、不做线上部署、不做域名与反向代理
- 不做分校区 / 多租户隔离

## 2. 角色与核心流程

### 谁发布什么

这是本系统的核心约定，先说清楚：

| 角色 | 能发布的内容 | 发布后的初始状态 |
| --- | --- | --- |
| 管理员 | `found` 招领物品 —— 失物招领柜里实际放着的东西 | `approved`，直接公开，不需要审核 |
| 学生 | `lost` 寻物启事 —— 「我丢了一个黑色钱包，看到请联系我」 | `pending`，管理员通过后才公开 |

物品进入柜子由管理员执行，学生不能往柜子里添加物品。管理员登记的物品不存在
「自己审自己」的问题，所以登记即公开。

### 学生

1. 用学号 + 姓名 + 密码注册，或用学号 + 密码登录
2. 登录后进入工作台，看到的就是失物招领柜：柜子里全部在库物品的卡片列表
3. 用关键词搜索，按类型、状态筛选，翻页
4. 打开详情看大图和完整描述（拾获地点、拾获日期、存放位置与联系方式），
   认出是自己的东西就填一段认领说明提交申请
5. 在「我的申请」里查看自己提交过的认领申请及其处理结果
6. 也可以发布寻物启事（标题、描述、地点、日期、联系方式，可选一张图），
   等管理员审核通过后公开
7. 在「我的发布」里编辑或删除自己的寻物启事

### 管理员

1. 用管理员账号 + 密码登录
2. 登记物品：填写名称、描述、拾获地点、拾获日期、存放位置与联系方式，上传一张照片，
   提交后直接进柜子，学生立刻能看到
3. 处理认领：查看待处理的认领申请，核对说明后同意或拒绝；同意后物品自动标记为已归还
4. 信息管理：查看全部状态的信息，可搜索、可编辑、可删除、可手动标记已归还
5. 审核：查看学生发布的待审核寻物启事，通过或驳回（可填写驳回原因）
6. 用户管理：查看学生列表，封禁或解封
7. 数据概览：在库数、已归还数、待审核数、注册用户数

### 物品状态流转

```
招领物品（管理员登记）
  登记 → approved（在柜中，公开可见）
            └── 认领被同意 / 手动标记 → returned（已归还，默认不在柜子列表里）

寻物启事（学生发布）
  发布 → pending（待审核）
            ├── 管理员通过 → approved（公示中，公开可见）
            │                  └── 发布者本人标记 → returned（已找回）
            └── 管理员驳回 → rejected（仅本人和管理员可见）
```

### 认领状态流转

```
学生提交 → pending ── 管理员同意 → approved（物品同时自动变成 returned）
                   └─ 管理员拒绝 → rejected（物品保持 approved，其他人仍可申请）
```

同意一条申请时，同一条物品上其他还处于 `pending` 的申请自动变成 `rejected`，
避免一条物品被两个人领走。

## 3. 技术方案

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 服务端 | Node.js 24 内置 `node:http` | 不引入 Express 等框架，手写最小路由 |
| 数据库 | Node.js 24 内置 `node:sqlite` | 单文件数据库，零第三方依赖 |
| 密码与令牌 | `node:crypto` | `scrypt` 加盐哈希、`randomBytes` 生成会话令牌 |
| 测试 | `node:test` + `node:assert` | 内置测试运行器 |
| 前端 | 原生 HTML / CSS / JavaScript | 与已有 `todo-list` 项目风格保持一致 |

选型理由：这台开发机上没有 npm、没有 Python，Java 缺少构建工具，而 Node 24 已经内置了 HTTP 服务、
SQLite 驱动、加密和测试运行器。整套系统不需要安装任何第三方包，`node server.js` 即可运行，
也不依赖网络下载。

### 运行方式

```bash
cd lost-found
node server.js          # 启动服务，默认 http://localhost:3000
node --test "tests/*.test.js"   # 运行接口测试
node scripts/seed-demo.js   # 写入一批演示数据（可选）
```

端口通过环境变量 `PORT` 覆盖，数据库路径通过 `DB_PATH` 覆盖。

## 5. 数据模型

时间统一存 ISO-8601 字符串（UTC），在界面上按本地时区展示。

### users

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | PK AUTOINCREMENT | |
| username | TEXT | NOT NULL UNIQUE | 登录账号。学生填学号，管理员填账号 |
| name | TEXT | NOT NULL | 姓名 / 显示名 |
| password_hash | TEXT | NOT NULL | scrypt 派生结果（hex） |
| password_salt | TEXT | NOT NULL | 每个用户独立的随机盐（hex） |
| role | TEXT | NOT NULL, `student` / `admin` | 角色 |
| status | TEXT | NOT NULL, `active` / `banned` | 被封禁后不能登录，已有会话失效 |
| created_at | TEXT | NOT NULL | |

演示账号在首次启动建表后自动写入：

| 角色 | 账号 | 密码 |
| --- | --- | --- |
| 管理员 | `123` | `456` |
| 学生 | `111` | `222` |

### items

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | PK AUTOINCREMENT | |
| user_id | INTEGER | NOT NULL, FK users(id) | 登记者（管理员）或发布者（学生） |
| type | TEXT | NOT NULL, `lost` / `found` | `lost` 寻物启事（学生发布），`found` 招领物品（管理员登记，即在柜物品） |
| title | TEXT | NOT NULL | 标题，1–60 字 |
| description | TEXT | NOT NULL | 详细描述，1–1000 字 |
| place | TEXT | NOT NULL | 地点，1–60 字 |
| happened_at | TEXT | NOT NULL | 丢失 / 拾取日期，格式 `YYYY-MM-DD` |
| contact | TEXT | NOT NULL | 联系方式，1–100 字 |
| photo | BLOB | NULL | 图片二进制，最多 2MB |
| photo_type | TEXT | NULL | 图片 MIME 类型 |
| status | TEXT | NOT NULL, `pending` / `approved` / `rejected` / `returned` | `approved` 对 `found` 表示「在柜中」、对 `lost` 表示「公示中」；`returned` 表示已归还 / 已找回 |
| review_note | TEXT | NULL | 审核意见 / 驳回原因 |
| reviewed_by | INTEGER | NULL, FK users(id) | 审核人 |
| reviewed_at | TEXT | NULL | 审核时间 |
| created_at | TEXT | NOT NULL | |
| updated_at | TEXT | NOT NULL | |

`type` 与发布者角色绑定：`found` 只能由管理员登记，`lost` 只能由学生发布，
由 `POST /api/items` 按当前登录角色决定类型与初始状态，客户端传 `type` 一律忽略。

### claims

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | PK AUTOINCREMENT | |
| item_id | INTEGER | NOT NULL, FK items(id) ON DELETE CASCADE | |
| user_id | INTEGER | NOT NULL, FK users(id) | 申请人 |
| message | TEXT | NOT NULL | 认领说明，1–500 字 |
| status | TEXT | NOT NULL, `pending` / `approved` / `rejected` | |
| created_at | TEXT | NOT NULL | |
| decided_at | TEXT | NULL | |

约束：

- 同一用户对同一条物品只能有一条待处理的申请
- 只能对 `found` 类型且 `status = approved`（在柜中）的物品提交申请
- 管理员同意一条申请时，该物品自动变为 `returned`，该物品上其他 `pending` 申请自动变为 `rejected`

### sessions

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| token | TEXT | PK | `randomBytes(32)` 的 hex |
| user_id | INTEGER | NOT NULL, FK users(id) ON DELETE CASCADE | |
| created_at | TEXT | NOT NULL | |
| expires_at | TEXT | NOT NULL | 默认 7 天 |

索引：`items(status, created_at)`、`items(type, status, created_at)`、`items(user_id)`、
`claims(item_id)`、`claims(user_id)`、`sessions(user_id)`。

## 6. 接口设计

统一前缀 `/api`，请求与响应均为 JSON（图片上传除外）。带 `sid` Cookie 的请求会自动识别登录身份。

### 认证

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/student/register` | 公开 | 学号 + 姓名 + 密码注册 |
| POST | `/api/student/login` | 公开 | 学号 + 密码登录 |
| POST | `/api/admin/login` | 公开 | 管理员账号 + 密码登录 |
| POST | `/api/logout` | 登录 | 销毁当前会话 |
| GET | `/api/me` | 登录 | 返回当前用户信息 |

### 物品

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/items` | 公开 | 物品柜列表，支持搜索 / 筛选 / 分页，默认只返回 `approved`（在柜中 / 公示中） |
| GET | `/api/items/:id` | 公开 / 登录 | 详情，非 `approved` 的信息仅作者与管理员可见 |
| POST | `/api/items` | 登录 | 登记 / 发布，`multipart/form-data`，照片选填。管理员只能发 `found`（→ 直接 `approved`），学生只能发 `lost`（→ `pending`） |
| PUT | `/api/items/:id` | 作者或管理员 | 修改内容（含替换照片）；学生的寻物启事修改后回到 `pending` 重新审核，管理员修改不改变状态 |
| DELETE | `/api/items/:id` | 作者或管理员 | 删除 |
| GET | `/api/items/:id/photo` | 同详情 | 返回图片二进制，带正确 `Content-Type` |
| POST | `/api/items/:id/claims` | 学生 | 对在柜的 `found` 物品提交认领申请 |
| GET | `/api/my/items` | 登录 | 我登记 / 发布的（含各状态与收到的申请数） |
| GET | `/api/my/claims` | 学生 | 我提交的申请 |
| POST | `/api/claims/:id/decision` | 登记人或管理员 | 同意或拒绝认领；同意时自动把物品标记为已归还，并驳回该物品其他待处理申请 |
| POST | `/api/items/:id/return` | 登记人或管理员 | 手动标记为已归还（失主直接来办公室领取的情况） |

### 管理

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/admin/items` | 管理员 | 全部物品与寻物启事，可按状态与关键词搜索 |
| POST | `/api/admin/items/:id/review` | 管理员 | 审核学生发布的寻物启事：通过 / 驳回 |
| GET | `/api/admin/users` | 管理员 | 学生列表，可按学号 / 姓名搜索 |
| POST | `/api/admin/users/:id/status` | 管理员 | 封禁 / 解封 |
| GET | `/api/admin/stats` | 管理员 | 数据概览 |

### 响应约定

列表类接口统一返回：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 12,
  "total": 0,
  "totalPages": 0
}
```

错误统一返回：

```json
{ "error": { "code": "INVALID_INPUT", "message": "学号不能为空" } }
```

| 状态码 | 场景 |
| --- | --- |
| 400 | 参数校验失败 |
| 401 | 未登录或会话已过期 |
| 403 | 已登录但无权限（含账号被封禁） |
| 404 | 资源不存在 |
| 409 | 冲突，例如学号已被注册、重复提交待处理申请、物品已被领走不能再认领 |
| 413 | 图片超过大小限制 |
| 415 | 图片类型不支持 |
| 500 | 服务端异常 |

### 可见性与权限细则

这些规则容易在设计里被写含糊，先钉死：

- `contact`（联系方式）**不出现在列表接口**里；详情接口只对**已登录**用户返回该字段，未登录访问时该字段为 `null`
- 非 `approved` 状态的条目，只有作者本人（登记的管理员 / 发布的学生）和任意管理员能访问详情，
  其他人一律 404（不泄露"存在但被驳回"这一信息）
- `happened_at` 使用 `YYYY-MM-DD` 日期格式并由服务端校验；`created_at`、`updated_at`、`reviewed_at`
  等系统时间使用完整的 ISO-8601 时间戳
- 用户管理接口只返回和操作 `student` 角色的账号，管理员账号不出现在列表里，也不能被封禁
- 删除一条信息会连带删除它收到的认领申请（数据库外键 `ON DELETE CASCADE`）

## 7. 搜索与筛选（重点）

搜索是这个系统的核心功能之一，按下面的规则实现。

### 服务端

`GET /api/items` 支持以下查询参数，可以任意组合：

| 参数 | 说明 |
| --- | --- |
| `q` | 关键词，模糊匹配 `title`、`description`、`place` 三个字段 |
| `type` | `lost` / `found`，不传表示不限 |
| `status` | 公开列表可选 `approved`（默认，在柜中 / 公示中）、`returned`（已归还）、`all`（全部已公开的）；管理端接口另外支持 `pending`、`rejected` |
| `page` | 页码，默认 1，最小 1 |
| `pageSize` | 每页条数，默认 12，最大 50 |

实现细节：

- `q` 先做 `trim()`，空字符串视为不传；长度超过 50 字按 400 处理
- 使用参数化查询 + `LIKE`，并对 `%`、`_`、`\` 三个通配符字符做转义，配合 `ESCAPE '\'`，
  保证用户输入的 `%` 被当成普通字符而不是通配符
- 匹配大小写不敏感（`LIKE` 对 ASCII 默认不敏感；中文按原样子串匹配）
- 关键词与类型、分页条件是 AND 关系，全部拼在同一条 SQL 里，不做内存过滤
- 返回结果附带 `total`，用于界面显示"共 N 条结果"

管理端 `GET /api/admin/items` 复用同一套搜索逻辑，区别是可以指定 `status` 查看待审核等状态。

### 前端

- 学生工作台和管理后台都有搜索框，放在列表上方显眼位置
- 输入停止 300ms 后自动搜索（防抖），按回车立即搜索，不必点按钮
- 提供「清空」按钮，一键恢复未过滤状态
- 搜索条件变化时重置回第 1 页，避免停留在越界页码
- 结果为空时显示明确文案，例如「没有找到与"钥匙"相关的信息」，而不是一片空白
- 搜索条件与类型 / 状态筛选可叠加，界面上用标签显示当前生效的条件
- 物品柜默认只显示在柜中的物品，顶部提供「只看在柜 / 包含已归还」的切换，
  避免学生看到一条已归还的物品却以为它还放在办公室

| `student.html` | 顶部身份与退出；物品柜搜索与筛选栏；在柜物品卡片列表（缩略图、名称、类型徽章、拾获地点、拾获日期、状态）；详情（大图 + 认领申请入口）；发布寻物启事表单；我的发布；我的申请 |
| `admin-login.html` | 管理员登录表单 |
| `admin.html` | 数据概览卡片；登记物品表单（含照片上传与预览）；待处理认领申请列表；待审核寻物启事队列；全部条目表格（含搜索与状态筛选）；用户管理表格 |

交互约定：

- 列表项显示类型徽章（寻物 / 招领）和状态徽章（待审核 / 在柜中 / 公示中 / 已归还 / 已驳回），颜色区分
- 所有异步操作期间按钮进入禁用状态并显示"处理中"，避免重复提交
- 操作结果用页面顶部的轻提示条反馈（成功 / 失败），不使用 `alert`
- 表单错误在对应字段下方就地提示
- 用户输入一律用 `textContent` 写入 DOM，不拼接 HTML 字符串
- 窄屏（≤480px）下卡片与表格改为纵向排列，不出现横向滚动
- 键盘可达：Tab 顺序合理，交互元素带 `:focus-visible` 轮廓，搜索框、登录表单支持回车提交
- 登记物品时照片为选填；选好文件后立即在表单里预览缩略图，并可一键移除
- 列表缩略图缺失时显示占位块，不出现破图图标
- 认领按钮在物品已归还、或自己已经提交过申请时禁用，并在旁边写清楚原因
- 物品卡片上突出「在柜中 / 已归还」状态徽章，这是学生最关心的信息

## 9. 认证与安全

- **密码存储**：`scrypt(password, salt, 64)`，盐为 16 字节随机值，每个用户独立；校验用 `timingSafeEqual`
- **会话**：登录成功后生成 32 字节随机令牌，写入 `sessions` 表，有效期 7 天
- **会话清理**：服务启动时清理一次已过期的会话；鉴权时如果命中的会话已过期，删除该行并按未登录处理
- **Cookie**：`sid=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800`，前端 JS 读不到令牌
- **鉴权中间件**：每个受保护接口都解析会话 → 取用户 → 检查 `status`，封禁用户立即失效
- **权限检查**：学生只能改删自己的发布，且不能发布 `found` 类型；学生不能访问 `/api/admin/*`；
  认领决策只有物品的登记人或管理员可做；任何人都不能对自己登记 / 发布的东西提交认领申请
- **SQL 注入**：全部使用参数化查询，包括 `LIKE` 模式串
- **XSS**：前端不用 `innerHTML` 写用户内容；由 `node:http` 返回 JSON 时设置 `Content-Type: application/json`
- **上传**：限制 MIME 为 `image/jpeg`、`image/png`、`image/webp`，限制 2MB，
  校验文件头魔数与声明的类型是否一致，图片以 BLOB 存库避免文件系统残留
- **拒绝服务的基本防护**：请求体大小上限（图片 2MB、JSON 64KB），超出直接返回 413
- **密码不出现在任何日志与响应里**

说明：这是课程 / 面试用项目，未做 HTTPS、CSRF Token、登录失败次数限制、验证码等生产级加固，
这些在"后续计划"中列出。

## 10. 错误处理约定

- 服务端所有处理器返回统一结构，未捕获异常由顶层兜底为 500 并记录日志，不把堆栈返回给客户端
- 数据库操作失败（例如唯一约束冲突）转换为对应的 409，而不是 500
- 前端 `api.js` 统一解析错误结构，401 时跳转到对应登录页，403 显示"没有权限"，其余显示服务端返回的
  `message`，网络异常显示"网络连接失败，请重试"
- 列表加载失败时保留上一次的结果并提示，不清空页面

## 11. 测试策略

### 接口测试（`node:test`）

每个测试文件用独立临时数据库与随机端口启动服务，测试之间互不影响。覆盖：

- **认证**：注册成功、重复学号 409、空字段 400、密码错误 401、封禁用户不能登录、
  未登录访问受保护接口 401、退出后会话失效
- **信息**：登记参数校验、图片类型与大小限制、列表分页边界、搜索结果正确性
  （含 `%` 被当普通字符、只匹配标题不匹配描述的情况）、非 `approved` 对他人不可见、
  越权修改 / 删除被拒、作者可以删除自己的条目、管理员登记的物品立即公开且不需要审核、
  学生无法发布 `found` 类型、客户端传 `type` 被忽略
- **认领**：不能认领自己登记 / 发布的物品、不能认领已归还的物品、重复申请 409、
  只有登记人或管理员能决策、同意后物品自动变为 `returned` 且其他待处理申请自动变为 `rejected`、
  拒绝后物品仍保持在柜中
- **管理**：非管理员访问管理接口 403、审核通过后信息出现在公开列表、驳回后不出现、
  封禁用户后其会话立即失效、统计数字与实际数据一致

### 页面端到端冒烟

用无头 Edge（Chrome DevTools Protocol）跑一条主流程：管理员登录 → 登记一条带照片的招领物品 →
学生登录后在物品柜里搜索到它 → 打开详情提交认领申请 → 管理员同意 → 物品变为已归还、
从默认的在柜列表里消失，并在关键步骤断言页面上的可见文本与持久化结果。
